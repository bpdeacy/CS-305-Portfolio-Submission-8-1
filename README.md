# CS 305 Portfolio Reflection

For this course, I chose to include my Artemis Financial Practices for Secure Software Report as my portfolio artifact. Artemis Financial was the client for this project. The company provides individualized financial plans for customers, including savings, retirement, investment, and insurance services. Artemis Financial wanted to modernize its software and improve protection for client data and financial information. The main issue I addressed was adding secure communication and file verification features to the existing web application.

One thing I did well was identifying how security had to be handled in layers instead of depending on one fix. In Project One, I reviewed the application for weaknesses such as insecure coding patterns, outdated dependencies, missing input validation, and weak error handling. In Project Two, I refactored the application to support HTTPS communication and added a SHA-256 checksum endpoint. Coding securely is important because working code is not automatically safe code. Software that handles financial data needs confidentiality, integrity, and reliability. Strong software security adds value to a company by reducing risk, protecting customer trust, supporting compliance, and preventing avoidable damage from breaches or system misuse.

The most helpful part of the vulnerability assessment was learning to combine manual code review with automated static testing. Manual review helped me understand what the code was actually doing, while OWASP Dependency-Check helped identify known vulnerabilities in third-party libraries. The challenging part was separating vulnerabilities caused by my own code from vulnerabilities inherited through older framework dependencies. That distinction matters because the fix might be a code change, a configuration change, or a dependency upgrade.

I increased layers of security by adding HTTPS on port 8443, using a self-signed certificate generated with Java Keytool, and implementing a SHA-256 checksum through Java’s MessageDigest class. In the future, I would continue using manual review, static analysis, dependency scanning, vulnerability databases such as the NVD, and secure coding checklists to assess vulnerabilities and decide which mitigation techniques are appropriate. I would also consider the severity of each issue, whether the vulnerable code path is reachable, and how the vulnerability affects confidentiality, integrity, and availability.

To make certain the code and application were functional and secure, I ran the refactored Spring Boot application and verified that it started successfully over HTTPS. I also tested the /hash endpoint in the browser to confirm that it displayed the data string, SHA-256 algorithm name, and checksum value. After refactoring, I ran OWASP Dependency-Check again to check whether my changes introduced new vulnerabilities. The scan still showed known vulnerabilities from the existing project dependencies, but the added checksum code used Java’s built-in MessageDigest class and did not require adding new third-party libraries.

The resources and tools I used that will be helpful in future work include Java Keytool, Java’s MessageDigest class, OWASP Dependency-Check, Maven, the National Vulnerability Database, and secure coding practices such as avoiding weak algorithms, validating inputs, using HTTPS, reviewing dependencies, and handling errors carefully. These are practical tools and habits that apply beyond this course, especially in software projects that involve sensitive data or public-facing applications.

For future employers, I would show the Practices for Secure Software Report because it demonstrates both technical and security-focused work. It shows that I can review an application, identify security concerns, apply cryptographic tools, configure HTTPS, test the application after refactoring, and explain my decisions clearly. This artifact also shows that I understand security as part of the software development process, not something separate from it.
